# HR 三支柱角色、权限点与租户自定义角色

_Status: accepted, 2026-10-04；细化 ADR-0012 的多角色权限模型，废弃其中单一 `hr` 角色。_

## 背景

ADR-0012 确立了「角色集合 + 激活角色」的多角色方向，但落地时 HR 被建成一个包揽全部人事写权限的"大箩筐"角色，且两个欠账逐渐暴露：

1. **真实企业的 HR 按三支柱分工**：COE（专家中心，又分干部管理/绩效管理/薪酬激励/招聘运营/组织与人才发展五个板块）、HRBP（业务伙伴，按 BU 服务）、SSC（共享服务，处理事务与数据）。一个 `hr` 角色无法表达这种分工；每个部门的领导同样承担人员管理职责，需要自动获得与其组织位置匹配的权限。
2. **Juno 是 SaaS**：不同企业的组织与分工不同，权限必须允许租户自主配置，而不能把七张角色面孔焊死在代码里。
3. ADR-0012 承诺的"切换激活角色后服务端重算数据范围与掩码"只在原型前端实现，后端 `has_any` 实际按角色集合并集放行——切到员工视角的人仍能调用 HR 接口，掩码会失效。

## 决策

### 1. 角色枚举：废弃 HR，拆为七角色

后端 `Role` 枚举移除 `HR`，新增：

| 枚举 | 界面显示名 | 默认数据范围 |
|---|---|---|
| `HR_COE_CADRE` | COE·干部管理 | 全租户 |
| `HR_COE_PERF` | COE·绩效管理 | 全租户 |
| `HR_COE_COMP` | COE·薪酬激励 | 全租户 |
| `HR_COE_RECRUIT` | COE·招聘运营 | 全租户 |
| `HR_COE_OTD` | COE·组织与人才发展 | 全租户 |
| `HRBP` | HRBP（业务伙伴） | 按授权部门（含子树） |
| `SSC` | SSC（共享服务） | 全租户 |

其余角色不变：`EMPLOYEE / MANAGER / REVIEWER / LEAD_REVIEWER / EXECUTIVE / COMMITTEE / TENANT_ADMIN / PLATFORM_ADMIN`。reviewer/lead_reviewer 仍在前端合并映射为 `cert_panel`。五板块的默认权限矩阵（RACI、字段归属）见 prd.md 权限章节，矩阵是**默认模板的内容**，不是代码里的硬编码分支。

### 2. L2 权限模型：权限点目录 + 内置模板 + 租户自定义角色

- 平台代码发布一份**权限点目录**（约 24 个模块动作点 + 4 个敏感字段点，如 `inventory.batch.create`、`employee.salary.view`），粒度为"一组端点/一个字段段"，不做按钮级碎点。后端守卫由 `require_roles(...)` 统一重构为 `require_perm("<code>")`。
- 七个 HR 角色与 MANAGER 是**版本化的内置角色模板**（代码常量，即默认矩阵）。内置模板**不可直接修改**，租户要偏离时只能"克隆为自定义角色后编辑"——保证平台升级时新增权限点可统一演进。
- 租户管理员可在目录内组合创建**自定义角色**（如"行政·兼 SSC""综合 HR（一人全包）"），但**不能自创目录外权限点**。自定义角色对平台未来新增的权限点一律默认拒绝。
- `EMPLOYEE / EXECUTIVE / COMMITTEE / REVIEWER / LEAD_REVIEWER / TENANT_ADMIN / PLATFORM_ADMIN` 为系统固定角色，不可克隆。
- 系统角色/权限变更全部写审计日志；至少保留一个全权限管理员，防止自锁；薪酬查看点授予自定义角色时二次确认但不阻止。
- 种子与初始化向导提供"**综合 HR（一人全包）**"预设：七模板权限点并集 + GLOBAL 范围，服务没有三支柱分工的小租户；演示账号 hr@juno.test 挂该预设。

### 3. 数据范围四档

自定义/内置角色都绑定一种范围类型：`SELF`（仅本人）、`SUBTREE`（所辖部门子树，部门领导型，按部门树实时推导）、`ASSIGNED_DEPTS`（挂角色时逐条授权若干部门，含子树，HRBP 型）、`GLOBAL`（全租户）。不做条件式数据规则引擎（L3）。范围外员工**完全不可见**（不是掩码），名册、搜索、详情、AI 问答上下文同一口径。

### 4. 部门实体化与领导自动获权

- 新增 `departments` 表（id/tenant_id/name/parent_id/type/leader_employee_id + 时间戳），将 org.py 中 19 行静态部门树扶正为主数据；`employees.dept_id` 改为外键并迁移；岗位编制表本期不实体化。
- 部门设置 leader 时，系统**自动向该员工角色集合授予/回收 MANAGER 角色**（方案 A）：权限判定路径保持单一，现有所有 `MANAGER` 守卫与"汇报链 + 部门子树"推导逻辑复用。MANAGER 仍可手工授予，作为虚线领导/项目经理的补充通道。
- 部门领导可见本部门及下级子树 + 直接汇报链；敏感字段掩码；不看平级/上级部门。校准会横向对比走"流程内知情"：被 HRBP 加入某批次评估人名单后，仅在该批次会议范围内可见覆盖人员的评级定位，名册与档案页仍隔离。

### 5. 激活角色服务端强制

JWT 携带用户的角色实例集合（含租户自定义角色 id）；前端每个请求带 `X-Active-Role`（缺省回落主角色）。后端校验该角色属于本人后，**仅以这一个激活角色的权限点与范围类型**计算操作权、数据范围与字段掩码，不做并集。权限点随请求实时从库中计算（不写入长期 JWT），角色与权限变更下次请求即生效。

### 6. 薪酬激励角色的最小落脚点

新增员工定薪字段（月薪 + 最近调薪日期）与租户可覆盖的薪级带宽映射表（原静态 CHANNELS 的 salary_band），使 COE·薪酬激励 在 MVP 有真实功能；调薪流程、奖金、长期激励不在本期。定薪数据仅 `HR_COE_COMP` 与 `TENANT_ADMIN` 可见明文，其余全部角色（含其他四个 COE）掩码。

## 后果

- 本次重构面：后端全部约 30 个端点的守卫、JWT/中间件、部门表与 scope/自定义角色表、枚举迁移（项目未上线，旧 `hr` 值同版本迁移后直接移除，不背兼容包袱）、251 个既有测试；原型前端 RoleCode/registry 角色矩阵、RoleSwitcher、档案页字段锁段、新增"角色与权限"管理页。
- 获得：三支柱分工可表达、SaaS 租户可自助配置、激活角色在服务端真正闭环、部门领导授权自动化、掩码有了字段级执行点；失去：一次跨全栈的大改，以及"内置角色即代码分支"的简单性——此后新增功能必须同步登记权限点目录与内置模板。
- 五体系（标准/选聘/评价/激励/发展）与五个 COE 板块的对应关系，使权限点目录与 COE 导航天然按体系分组，另见 ADR-0015。
