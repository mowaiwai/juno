# 员工与管理端统一为 Web 优先、多角色可切换，小程序后置

_Status: accepted, 2026-09-27；修订 ADR-0008 的员工触达通道结论。_

## 背景

ADR-0008 以「一线员工没有电脑、需要移动端触达」为由，将员工侧默认通道定为微信小程序。但在完整产品设计阶段发现两个更重的事实：

1. **同一自然人常持多角色**：部门经理同时是认证小组成员、HRD 同时是任职资格管理委员会成员、员工本人也可能是后备 B 角。若员工在小程序、管理者在 Web，同一个人要在两套系统间切换，待办、画像、认证数据被端割裂。
2. 角色差异的本质是「数据范围 + 字段掩码」，用一套 RBAC 体系在单一应用内解决，比维护两个端更简单，也更利于向客户演示「不同角色看到不同世界」。

## 决策

- **单一 Web 应用承载全部角色**（员工 / 管理者 / HR / 认证小组 / 管委会 / 高管 / 租户管理员 / 平台管理员）。
- 权限模型为「角色集合 + 当前激活角色」：同一时刻只有一个激活角色，切换后导航菜单、数据范围（本人 / 所辖子树 / 全公司）、敏感字段掩码（薪酬、测评、画像）全链路重算；不做权限并集视图，避免掩码失效。
- **员工自助页面集做响应式适配**，在手机浏览器与微信内可用；管理后台不做移动适配。
- **微信小程序后置为可选触达通道**：仅当客户明确需要微信生态深度能力（扫码、模板消息、原生拍照体验）时再启动。现有 `hr-saas/miniprogram/` 骨架原样保留、暂停投入。

## 后果

- 多角色切换成为正式产品设计（而非原型权宜）：需要登录态携带角色集合、激活角色可校验，数据范围与字段掩码在服务层强制执行，不能只靠前端藏菜单。
- 获得：一套代码、一套待办、演示连贯；失去：一线员工的原生 App 级触达体验，由移动 H5 响应式兜底，此代价明确接受。
- 原型工程（`prototype/`，分支 `prototype/full-product`）按本决策建设，并成为未来真实 Web 管理端的视觉与交互蓝本。
